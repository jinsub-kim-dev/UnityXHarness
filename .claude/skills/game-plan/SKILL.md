**$ARGUMENTS** — 이 입력으로 게임 기획 문서를 작성한다.

이 문서는 이후 기능별 PRD(`/prd`)와 구현 작업의 출발점이 된다. Key Systems의 각 항목이 구현 단위가 되고, Feature Priority와 Development Order가 무엇을 먼저 만들지 결정한다. 그래서 범위와 레퍼런스는 Claude가 임의로 확정하지 않고 반드시 사용자와 합의한다 — 잘못 확정된 범위는 이후 모든 PRD와 구현을 같이 틀어지게 만든다.

문서는 한국어로 작성한다. (섹션 제목은 아래 템플릿의 영문 그대로 둔다.)

## 1. 입력 파악

다음 세 가지가 필요하다.

- 장르
- 핵심 루프
- 주요 시스템 목록

`$ARGUMENTS`나 대화에서 빠진 항목이 있으면 빠진 것만 짧게 묻고 답을 기다린다. 핵심 루프나 시스템이 모호할 때(예: "전투"만 있고 실시간인지 턴제인지 불분명)도 추측하지 말고 묻는다.

`docs/design/game-plan.md`가 이미 있는지 확인해 둔다 (5단계에서 사용).

## 2. 레퍼런스 후보 제시

같은 장르라도 대표작마다 루프와 시스템 구성이 크게 다르므로, 어떤 게임을 기준으로 삼느냐가 기획 전체의 방향을 바꾼다.

- WebSearch로 입력된 장르·핵심 루프와 유사한 게임을 찾는다. 기억에만 의존하지 말고 검색해서 실제 존재하는 게임인지, 특징이 맞는지 확인한다
- 후보를 **3~5개** 제시하고, 각 후보에 핵심 루프·차별점을 한 줄로 붙인다

```
1. <게임명> — <핵심 루프 / 차별점 한 줄>
2. ...
```

- 그 다음 **어떤 게임(들)을 레퍼런스로 삼을지** 묻고 답을 기다린다. 여러 개를 고르거나 목록에 없는 게임을 지정해도 된다. 사용자가 고르기 전에 다음 단계로 넘어가지 않는다

## 3. MVP 범위 합의

선정된 레퍼런스의 루프·시스템 구성을 반영해, 입력된 주요 시스템과 레퍼런스에서 가져올 요소를 **MVP 후보**와 **나중 후보**로 나눈 제안을 보여준다. 각 항목 옆에 왜 그쪽에 두었는지 짧게 적는다 (예: "핵심 루프가 이것 없이 한 바퀴 돌지 않음").

MVP 판단 기준은 "핵심 루프가 처음부터 끝까지 한 바퀴 플레이 가능한 최소 구성"을 기본 제안으로 쓰되, 이 분류는 제안일 뿐이다. 사용자가 확정하거나 조정할 때까지 기다린다.

## 4. 초안 작성

합의된 내용으로 아래 템플릿의 섹션을 이 순서 그대로 채운다.

```markdown
# <게임 가제 또는 장르> 기획

## Game Concept
<이 게임이 주는 핵심 경험을 한 단락으로>

## Reference Games
- **<게임명>** — 참고할 요소: <루프 구조 / 특정 시스템 / 진행 방식 등>

## Core Loop
1. <단계> — <이 단계에서 일어나는 일>
   ↓
2. <단계> — <...>
   ↓
3. ...
   ↺ 1로 돌아감 (<무엇이 달라진 상태로 돌아가는지>)

## Key Systems
| 시스템 | 역할 | 연결되는 루프 단계 |
|---|---|---|
| <시스템명> | <이 시스템이 책임지는 것> | <Core Loop 단계 번호> |

## Feature Priority
### MVP
- <기능> — <MVP에 포함한 이유>

### 나중
- <기능> — <미룬 이유 또는 선행 조건>

## Development Order
1. <구현 대상> — <먼저 하는 이유 / 이것으로 확인할 수 있는 것>
2. ...
```

작성 요령:

- **Core Loop**는 순서도로 읽혀야 한다. 마지막 단계에서 처음으로 돌아갈 때 플레이어 상태가 무엇이 달라지는지(성장·보상·난이도) 적어야 루프가 "왜 반복되는지"가 드러난다
- **Key Systems**의 각 행은 나중에 PRD 하나·구현 작업 하나의 단위가 된다. 너무 크면(예: "게임 시스템") 쪼개고, 역할이 겹치는 시스템은 합친다
- **Feature Priority**는 이 문서에서 가장 중요한 섹션이다. 3단계에서 합의한 분류를 그대로 쓰고, 초안 작성 중 임의로 옮기지 않는다
- **Development Order**는 MVP 항목부터 의존 관계 순으로 배치한다. 가능한 한 이른 단계에서 핵심 루프를 실제로 플레이해볼 수 있게 하고, "나중" 항목은 MVP 이후에 둔다
- 입력이나 합의에서 나오지 않은 수치·세부 규칙은 지어내지 않는다. 필요하면 해당 위치에 `(미정)`으로 두고 리뷰 단계에서 질문으로 올린다

## 5. 리뷰 요청

- 초안 전체를 대화에 보여주고 수정할 부분이 있는지 묻는다. 아직 파일로 저장하지 않는다
- `(미정)` 항목이 있으면 함께 질문한다
- 피드백을 반영해 다시 보여주는 과정을 사용자가 승인할 때까지 반복한다
- `docs/design/game-plan.md`가 이미 있으면 이 단계에서 알리고 덮어쓸지 확인받는다. 확인 없이 덮어쓰지 않는다

## 6. 파일 저장

- 승인되면 `docs/design/game-plan.md`에 저장한다. 다른 위치에는 저장하지 않는다
- `docs/design/` 폴더가 없으면 만든다

## 7. 사용법 안내

저장 후 아래 메시지를 그대로 출력한다.

```
✅ docs/design/game-plan.md 저장 완료
다음 단계: Development Order 1번부터 기능별 PRD를 작성하세요.
예) /prd <Key Systems의 시스템명>
```
