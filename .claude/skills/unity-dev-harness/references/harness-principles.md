# 하네스 설계 원칙과 품질 기준

이 문서는 Unity 개발 하네스를 설계·생성할 때 지키는 규칙이다. 흐름은 SKILL과 `harness-design-workflow.md`, 구성요소 사양은 `agent-team-design.md`, 검증은 `testing-qa-evolution.md`를 따른다. 이 문서는 그 위에서 공통으로 지킬 판단 기준만 모은다.

## 기본 원칙

- Phase는 0부터 8까지로 고정한다.
- 하네스 생성은 반드시 청사진 승인 게이트를 지난다. 청사진을 먼저 보여주고, 명시적 승인 뒤에만 파일을 만든다.
- 파일보다 역할과 흐름을 먼저 제시한다.
- 산출물 우선으로 설계한다. 최종 결과(동작 스크립트 / 설계 문서 / 버그 패치 / 리팩토링 코드 / 플레이 가능한 씬)를 먼저 정하고 Agent·Skill을 뒤에서 설계한다.
- 정보가 부족하면 임의로 채우지 않고 `확인 필요`, `추가 입력 필요`, `사람 승인 필요`로 나눈다.
- 청사진과 실행 하네스에는 산출물 계약(어떤 파일을, 누가 만들고, 다음 단계가 무엇을 읽는지)을 포함한다.
- 코드·씬·에셋은 `Assets/` 정규 위치에, 설계·검토·기록 문서는 `artifacts/`에 둔다. 코드를 `artifacts/`에 두면 Unity가 컴파일하지 않는다.
- 실행 하네스 생성 위치: `.claude/agents`, `.claude/skills`, `.claude/hooks`, `CLAUDE.md`, `artifacts/`. 전역 위치는 설치·배포를 명시적으로 요청받을 때만 다룬다.
- 기존 `.claude/*`, `CLAUDE.md`가 있으면 먼저 읽고, 덮어쓰기 전에 변경 범위를 분명히 한다.
- `CLAUDE.md`에는 자연어 라우팅 규칙을 둔다. 스킬명을 직접 입력하지 않아도 게임 개발 작업으로 판단되면 `-orchestrator`를 먼저 사용하도록 안내한다.
- Orchestrator Skill은 폴더명·`name`이 `-orchestrator`로 끝난다. 일반 Skill은 이 접미사를 쓰지 않는다.
- 게임 범위와 작업 성격에 따라 Agent 구성을 조정한다. 고정 구성을 무조건 넣지 않는다.
- 하네스는 고정물이 아니다. 실행 기록·검증 실패·사용자 피드백을 바탕으로 작게 고쳐 간다.
- 실행 하네스는 후속 요청("다시", "기능 추가", "이 버그만", "이전 설계 기반")을 처리한다. Orchestrator description과 실행 모드 확인 단계에 분기 기준을 둔다.

## Unity 개발 안전 지점

- 검증은 4단계 게이트를 따른다(컴파일 → 런타임 에러 → 기능 점검 자동 → 기능 점검 사용자). 단계에서 막히면 다음으로 넘어가지 않고 보고·수정·재검증한다. 상세는 `testing-qa-evolution.md`.
- 씬·프리팹·에셋 변경은 사람 승인 지점이다. unity-ai-operator(MCP)에 위임하되 변경 전 요약을 보여주고 승인받는다.
- 에셋·씬 대규모 변경 전 커밋/백업을 권장 단계로 둔다(.meta 동반 변경).
- 기능 동작 최종 판정은 사용자 몫이다. 4단계 사용자 피드백을 검증에 포함한다.

## 품질 기준

- 게임 범위가 흐릿하면 최소 질문으로 차원/장르, 작업 성격, Unity MCP 연동 여부, 참조할 문서(코딩 컨벤션 등) 경로를 확정한다.
- Agent 수는 보통 3-4개, 최대 5개(unity-ai-operator 포함). 분리 기준은 `agent-team-design.md`.
- 각 Agent에는 책임·입력·출력·하지 말아야 할 일을, 각 Skill에는 트리거·절차·출력 형식·품질 체크를 둔다.
- Orchestrator에는 작업 순서, 산출물 계약, 4단계 검증 게이트, 실패 시 재시도/사람 확인 조건을 둔다.
- code-reviewer는 전체 완료 후 1회가 아니라 시스템·모듈 단위로 점진 검토한다.
- 검증 시 `.claude/commands/`를 만들지 않았는지 확인한다. 기준은 Agent, Skill, Orchestrator, hooks, `CLAUDE.md`, `artifacts/`다.
- 하네스 두께는 위험도에 맞춘다. 프로토타입은 얇게, 되돌리기 어려운 작업(씬 대규모 변경·에셋 삭제)은 검증·승인을 두껍게.

## 피해야 할 것

- 하네스가 모든 문제의 정답인 것처럼 제시하지 않는다.
- 생성 코드를 검증 없이 정답처럼 제시하지 않는다.
- C# 코드를 `artifacts/`에 두지 않는다.
- Phase 번호·명령 이름을 문서마다 다르게 쓰지 않는다.
- 처음부터 디렉터리 구조와 YAML만 보여주지 않는다.
- 단순 스크립트 하나에 Agent를 과하게 늘리지 않는다.
- 씬 수정·에셋 생성/삭제·대규모 리팩토링을 사람 승인 없이 완료 처리하지 않는다.
- MCP 미연동 환경에서 MCP 도구를 전제로 한 하네스를 만들지 않는다. 연동 여부를 먼저 확인한다.

## 하네스 7요소

| 요소 | 확인 질문 |
| --- | --- |
| 목표 | 최종 결과물은 동작 스크립트? 시스템 설계? 버그 수정? |
| 컨텍스트 | 폴더 구조·네이밍·기존 Manager/시스템 중 무엇을 먼저 줄 것인가? |
| 도구 | Read/Edit만? Unity MCP까지? |
| 중간 산출물 | 구현 전 설계안(클래스 구조·책임 분리)을 먼저 확인할 것인가? |
| 검증 | 4단계 게이트의 각 단계 통과 기준은? |
| 권한과 승인 | 씬·에셋 변경, 대규모 리팩토링 전 누가 확인하는가? |
| 기록과 개선 | 어떤 설계 결정·버그 원인을 저장하고 다음번에 고칠 것인가? |
